# PRODUCT REQUIREMENTS DOCUMENT (PRD)

## 1. Product Overview

### 1.1. Product Name

**House Viewing Booking System**

### 1.2. Product Objective

Build a system that allows customers to search for properties, view property information, and schedule a house viewing at a preferred date and time.

Sales agents receive and process booking requests.

Administrators manage users, properties, sales agents, and bookings.

### 1.3. Core Value

The system digitizes the basic house-viewing booking process:

**Find a property → Select a property → Select a time → Create a booking → Sale confirms → Track booking status**

The MVP focuses on replacing manual booking processes through phone calls, messages, or spreadsheets with a centralized system.

---

# 2. Problem Statement

The current manual booking process may cause several problems:

* Customers may have difficulty finding and accessing property information.
* Customers need to contact sales agents directly to schedule a viewing.
* Sales agents may have difficulty managing multiple booking requests.
* Booking statuses such as Pending, Confirmed, or Cancelled are difficult to track.
* Administrators have limited visibility into users, properties, and bookings.
* Scheduling conflicts and time-related mistakes may occur.

### Core Problem

> How can customers schedule a house viewing by themselves while allowing sales agents to process bookings through a clear and trackable workflow?

---

# 3. Product Goals

## MVP Goals

1. Customers can register and log in.
2. Customers can search for and view properties.
3. Customers can create bookings.
4. Customers can view their bookings.
5. Customers can cancel bookings.
6. Sales agents can view assigned bookings.
7. Sales agents can confirm or reject bookings.

9. Sales agents can manage their availability.
10. Administrators can manage users, properties, sales agents, and bookings.

# 10. Booking

## FR-04: Create Booking

Customers select:

* Property
* Date
* Start time
* End time

The customer then confirms the booking.

A newly created booking has the status:

**PENDING**

### Business Rule

Each booking must be associated with:

* One Customer
* One Property
* One Sales Agent

The Sales Agent is responsible for processing the booking.

---

# 11. Booking Status

The MVP uses the following booking statuses:

```text
PENDING
   │
   ├── CONFIRMED
   │      │
   │      └── COMPLETED
   │
   ├── REJECTED
   │
   └── CANCELLED
```

### Status Definitions

**PENDING**

The customer has created a booking and the Sales Agent has not processed it yet.

**CONFIRMED**

The Sales Agent has confirmed the viewing appointment.

**REJECTED**

The Sales Agent cannot accept the booking.

**CANCELLED**

The booking has been cancelled by the customer or the system.

**COMPLETED**

The house viewing has been completed.

```text

 └── Booking
        ├── Property
```

### Design Rationale

Booking is the central entity of the business process.

A Booking answers three key questions:

> Who wants to view the property?

> Which property do they want to view?

> Which Sales Agent is responsible for the viewing?

# 17. UI/UX Principles

## Principle 1 — Make Booking Simple

The booking flow should be:

```text
Property
   ↓
Property Detail
   ↓
Book Viewing
   ↓
Select Date
   ↓
Select Time
   ↓
Confirm
```

Customers should not have to go through unnecessary screens or steps.

---

## Principle 2 — Make Status Clear

Customers should easily understand the current booking status:

* Pending
* Confirmed
* Rejected
* Cancelled
* Completed

---

## Principle 3 — Make Actions Clear

Use clear action labels such as:

* Confirm Booking
* Reject Booking
* Cancel Booking
* Complete Booking

Avoid ambiguous labels that may confuse users.

---

## Principle 4 — MVP First

Do not introduce complex dashboards, filters, settings, or interactions unless they directly support the core business flow.

# 19. Acceptance Criteria — MVP

The MVP is considered complete when the following scenarios work successfully.

### Scenario 1 — Create Booking

Customer logs in → searches for a Property → opens Property Details → creates a Booking successfully.

### Scenario 2 — Confirm Booking

Sales Agent logs in → sees a Pending Booking → confirms the Booking.

### Scenario 3 — Track Booking

Customer opens My Bookings → sees that the Booking status has changed to Confirmed.

### Scenario 4 — Reject Booking

Sales Agent rejects a Booking → Customer sees the Rejected status.

### Scenario 5 — Cancel Booking

Customer cancels a Booking → the Booking status changes to Cancelled.

### Scenario 6 — Availability

Customers can only request appointments during the Sales Agent's configured availability.

### Scenario 7 — Admin Management

Admin can view and manage Users, Properties, Sales Agents, and Bookings.

---

# 20. Success Criteria

The primary MVP success criterion is:

> A customer can complete the booking process from selecting a property to receiving confirmation from a Sales Agent without requiring manual communication outside the system.

# Product Principle

The overall product development principle is:

**Start with the core business problem → define the essential user flows → build the minimum required features → validate the workflow → expand gradually.**

The system should prioritize:

**Simplicity → Clear Workflow → Correct Booking Management → Extensibility**
